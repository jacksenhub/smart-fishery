## 1. 使用的方案

本仓库**没有引入任何第三方日志库**（如 winston、pino、bunyan、morgan、log4js 等）。后端采用两种并行的记录方式：

- **结构化系统日志（SystemLog）**：通过 `appendLog(level, title, detail, source)` 写入内存数组 `systemLogs`，持久化到 `data/platform-state.json`，并通过 `GET /api/logs` 暴露给前端。这是平台业务侧的“应用日志”。
- **进程标准输出/错误**：启动、UDP 发现、HTTP 监听、信号处理等基础设施级信息直接调用 Node.js 的 `console.log` / `console.warn` / `console.error`。

前端（Next.js 应用）未包含自定义日志模块，仅使用浏览器原生 `console.*`；构建产物中的 `next-dev.log` 由 Next.js 自身生成，不属于本项目代码。

## 2. 关键文件

| 文件 | 作用 |
|---|---|
| `apps/backend/src/index.ts` | 定义 `appendLog`、`systemLogs` 数组、`/api/logs` 端点，以及所有 `console.*` 调用 |
| `apps/backend/src/persistence.ts` | 负责将 `systemLogs` 与平台状态一起序列化到 `data/platform-state.json` |
| `packages/shared/src/index.ts` | 导出 `SystemLog` 类型（被 backend 导入），是日志条目结构的唯一来源 |
| `apps/frontend/.next-dev/dev/logs/next-development.log` | Next.js 开发服务器自行生成的日志（非项目代码） |

## 3. 架构与约定

### 3.1 结构化日志结构（SystemLog）

每个日志条目是一个对象，字段如下（来自 `@fishery/shared` 的 `SystemLog` 类型）：

- `id`: 通过 `crypto.randomUUID()` 生成
- `level`: 字符串级别，当前代码中实际使用的值包括 `success`、`info`、`warning`、`error`
- `title`: 中文摘要标题
- `detail`: 中文详细消息
- `source`: 来源标识，常见取值有 `system`、`demo`、`ai`、`twin-simulator`、设备 `device_id` 等
- `timestamp`: ISO 8601 时间戳

`appendLog` 的实现约定：
- 新条目 `unshift` 到数组头部
- 自动裁剪至最多 80 条（`systemLogs.splice(80)`）
- 每次写入后调用 `persistPlatformState()` 触发异步持久化

### 3.2 日志级别语义

| 级别 | 含义 | 典型调用位置 |
|---|---|---|
| `success` | 操作成功完成 | 平台启动、GPS 获得有效定位、舵机/推进控制板在线 |
| `info` | 常规业务事件 | 传感器数据接收、演示数据生成、舵机命令下发、数字孪生推演完成 |
| `warning` | 需要关注但非失败 | 推进器急停触发 |
| `error` | 失败或异常 | AI 报告生成失败、数字孪生推演失败 |

注意：级别不是通过枚举强约束的，而是自由字符串；当前实现只区分这四个值。

### 3.3 持久化策略

`systemLogs` 与 `waterHistory`、`batteries`、`latestAiReport` 一起作为平台状态的一部分，通过 `schedulePersistState` → `flushPersistedState` 写入 `data/platform-state.json`。重启时从该文件恢复 `systemLogs`，因此日志在进程重启后可见。

### 3.4 进程级输出

基础设施层使用 `console.log` / `console.warn` / `console.error` 直接输出到 stdout/stderr，包括：
- UDP 发现服务监听地址
- HTTP 服务监听地址与本地访问提示
- CORS 配置警告（当 `UISYS_API_TOKEN` 未配置时）
- UDP 错误、HTTP 启动错误
- SIGINT/SIGTERM 信号处理时的停止提示

这些输出**不进入** `systemLogs`，也不提供 API 读取，仅用于运维观察。

## 4. 约定与约束

- **禁止散落的 console 调用替代 appendLog**：业务事件（传感器数据、AI 报告、设备状态变更、推演结果）统一通过 `appendLog` 写入结构化日志；只有底层 I/O 错误、启动/关闭信息等基础设施场景才直接使用 `console.*`。
- **日志条目必须带 source**：`appendLog` 默认值为 `"system"`，但各调用方均显式传入具体来源（`demo`、`ai`、`twin-simulator`、`device_id` 等），便于按来源过滤。
- **日志量上限为 80 条**：`splice(80)` 保证内存和持久化体积不会无限增长。
- **日志级别为自由字符串**：代码未定义枚举或校验函数，新增级别不会被拒绝，但应遵循现有 `success/info/warning/error` 四档语义。
- **前端无服务端日志能力**：前端仅消费 `/api/logs` 展示历史，不产生新的日志条目。
- **固件（ESP32）侧**：仓库中的 `.ino` 文件未包含日志输出逻辑（仅 WiFi 配置），因此本项目的日志体系仅覆盖 Node.js 后端与前端。

## 5. 适用性判断

该项目存在明确的日志子系统（结构化 SystemLog + 进程 console 输出），但属于**轻量级自实现**，未使用第三方日志框架。整体可归类为“medium”——有固定模式与约定，但规模较小、功能有限。
